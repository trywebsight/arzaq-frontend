# Internationalization (`Accept-Language`)

The marketing site is **Arabic-only and RTL-first** today (`siteConfig.locale = "ar"`). The API must still honor `Accept-Language` from day one so adding `en` (or others) later does not require a breaking rewrite.

## Request

The Next.js client sends:

```http
Accept-Language: ar
```

(or a future UI locale). Backend resolves:

1. Exact tag match (`ar`, `en`)
2. Primary subtag (`ar-KW` → `ar`)
3. Fallback locale configured in Laravel (`ar`)

## Response rules

| Content | Behaviour |
| --- | --- |
| Translatable strings (`title`, `excerpt`, `description`, `kindLabel`, FAQ, SEO, settings labels) | Return the resolved locale |
| Enums / ids (`purpose`, `kind`, `governorate`, `slug`, `id`) | **Stable**, language-independent |
| Numbers | JSON numbers; display uses Western digits |
| Missing translation | Fall back to `ar`, never omit required fields |

## Suggested Laravel shape

Spatie Laravel Translatable (or equivalent) on:

- Property: `title`, `excerpt`, `kindLabel`, `city`, `district`, `address`, image `alt`
- Post: `title`, `excerpt`, `category`, sections, author role
- Service: `title`, `description`
- Team: `name`, `role` (names often identical across locales)
- FAQ, SEO, Home, Settings copy fields

Slugs: either one slug for all locales (simplest for v1) or per-locale slugs with a canonical — if per-locale, document redirect rules. **Frontend v1 assumes a single `slug`.**

## Frontend copy vs CMS

| Source | Role |
| --- | --- |
| `messages/ar.json` | UI chrome, empty/error strings, default marketing copy |
| API (localized) | Dynamic entities + optional CMS overrides |

Do not inline Arabic in React components. CMS overrides replace message keys only where explicitly wired (hero, SEO, settings).

## Direction

HTML stays `dir="rtl"` for `ar`. Future LTR locales need a locale→direction map in the Next.js layout — out of scope for API contract beyond returning the correct strings.
